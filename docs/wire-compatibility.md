# 远程线路兼容性契约（wire compatibility）

适用范围：web 客户端 ↔ 宿主 `RemoteServer` 的 `/ws` JSON 协议
（`src/shared/wsProtocol.ts`），以及经 relay 的对应透传帧。

前提：**混版本是常态，不是边缘情况**。web 页面可以在浏览器里开几天不关，
而 Electron 宿主随时升级；两端独立更新。改任何一端交换的东西之前，先读本文。

## 规则 1 —— 已有帧加可选字段：安全

所有读取方对未知字段天然忽略（JSON.parse + 显式取字段）。旧端从没听说过
该字段，就不会读它。例：`auth-ok.caps`。

**安全的前提是读者永远容忍缺失**。一旦新客户端开始「必须」读到它，该客户端
对所有旧宿主即坏——等价于删字段，只是发现得更晚。新行为依赖新字段时，
走规则 2 协商，或让读取方回退。

## 规则 2 —— 新帧类型不安全；必须经 caps 协商

旧 `parseClientMessage` 对未知 `type` 返回 null → 服务端 BAD_MESSAGE 断链；
旧客户端解码器对新帧静默丢弃。两种方向都是无声故障：发送方永远不知道，
对端的功能表现为「挂起」。

协商通道（已就位）：
- 客户端 → 宿主：`auth-response.caps`（string[]，≤16 项、每项 ≤32 字符
  `[a-z0-9-]`；解析失败整帧 BAD_MESSAGE）。
- 宿主 → 客户端：`auth-ok.caps`（同样式；空则整个字段省略，与旧版本
  线上行为逐字节一致）。
- 客户端侧 gate：`webSocketTransport.supportsCap(cap)`。**caps 缺失 =
  旧宿主 = 功能关闭**；`auth-ok` 在每次（重）连接都会重发，按新连接重置。
- 现有成员：`e2ee`（宿主可做 R-M4-B 端到端加密）。新成员按需追加，
  追加本身即规则 1。

## 规则 3 —— 改发布内容等同改线路

帧结构不动也可能破坏旧端：宿主停止填充某字段（旧客户端读到 undefined）、
字段的取值域变化、某帧的发送时机变化。评审时按线路变更对待。

## 硬约束

- 帧名 / 消息 type 一经发布**永久占用**，即使功能删除也不得复用。
- 字段名与 `ipcChannels.ts` 的 IPC payload 保持对齐（历史约定）。
- 解析器保持 total：永不 throw，畸形输入一律返回 null / 丢弃。
